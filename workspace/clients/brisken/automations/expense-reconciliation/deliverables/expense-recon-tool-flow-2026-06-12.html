How the expense reconciliation tool works

A plain walk through what happens when the tool is handed a month of card activity and a set of receipts: how it reads them, matches every charge to its receipt, sorts each line into the right account, and hands back a review sheet plus a Books-ready journal. Nothing posts to Zoho on its own; the last step stays yours.

The shape of one run

Six passes, left to right. Each one hands its result to the next.

1ReadLoad the statement and the receipts into one common shape.
2RememberFile the statement and receipts in the tool's own tables.
3SortPut every receipt line into one of eight categories.
4MatchPair each charge with its receipt.
5JudgeSend only the hard cases to a model for a second look.
6Hand backA review sheet plus a Books-ready journal.

The tool is run once per month with a small settings file that points at the two inputs and says where to write the outputs. One command does the whole pass. There is also a preview mode that runs everything and prints a summary without writing a single file, so a run can be checked before it is kept.

What goes in

Two things: the charges, and the proof for each charge.

The statement is the card or bank activity for the month, as a spreadsheet file. A small column map tells the tool which column holds the date, the amount, and the merchant, so the tool never hardcodes one bank's layout. A statement file can hold several cards at once; the Chase export does.

The receipts are the proof for each charge. The tool reads them from any of three sources, and the rest of the pipeline does not care which one was used:

Zoho Expense export

The main source today.

  • The expense lines already typed into Zoho Expense, exported as a file.
  • Each line carries its report number and a link to the attached receipt.
  • Read through the same column map idea, so no Zoho header name is baked in.

A typed-out file

The simple fallback.

  • A plain file with the receipt fields already filled in.
  • Useful for a quick one-off or a hand-built set.

A folder of images

For receipts that never went through Zoho.

  • Drop in photos and PDFs of receipts.
  • The tool reads the text off each one with OCR, which means reading text from a picture.
  • Digital PDFs are read from their text layer first, which is cheaper and more exact than reading the image.

The tool also pulls Brisken's chart of accounts (the list of real Books accounts) when a run is set up to write the journal, so it can name real accounts instead of placeholders.

Matching each charge to its receipt

A plain match first. A model only when a plain match cannot settle it.

The rule here is Dirk's: no model where a straightforward match already works. When a card charge and a receipt share the same card, the same day, and the same amount, the tool pairs them on the spot with full confidence and moves on. The model is never consulted for the easy majority.

When the currencies differ

Travel makes this the interesting part. A receipt in euros or reais sits against a charge that posted in dollars, so the amounts will not line up to the cent. The tool checks how far apart they are once converted, and sorts the pair into one of three bands. The width of each band came from real Brisken receipts, not a guess.

Within ~3% confident match 3% to ~13% conversion-fee suspect, send for a second look Over ~13% too far apart, hold it back

The wider band exists because of DCC, dynamic currency conversion, where the card does its own conversion at the till and adds a markup. On the Brisken receipts that markup ran from about 3.5% up to nearly 13%, so a charge can sit well above the network rate and still be the right receipt. The tool reads the dollar figure printed on the receipt when there is one, because Dirk's rule is to trust the printed dollar amount over an estimate.

When the merchant name is mangled

Banks truncate. The Chase export prints MEGA CENTE CONSTR for a shop whose full name runs to a dozen words. The tool compares the two names token by token and scores how close they are, so a chopped word still matches its full form. The name is a tie-breaker, never the only thing a match rests on.

Nothing is dropped

This is the promise the whole engine is built around. After the pass, every single charge has landed in exactly one of three places, and you can see the split at a glance:

Matched
Paired with its receipt and ready for the journal.
Needs your judgment
A currency case or a tie between two close receipts. Surfaced for review, with the model's read attached.
Unmatched
No receipt found, or no charge found. Flagged so the gap is visible, never hidden.

A charge can never vanish between the input and the output. If the tool cannot resolve something, it says so on the review sheet rather than guessing.

Sorting each line into an account

Eight categories, and a confidence floor under every call.

Before matching, the tool reads each receipt's line items and sorts them into one of eight categories: travel and transport, meals and entertainment, software and subscriptions, office supplies, equipment and hardware, marketing, professional services, and premises. It works from the line item itself, not from the merchant name, so a hardware charge at a general store still lands as hardware. Every call carries a confidence score, and anything under the floor is set aside for you rather than forced.

Tier 1From the lineRead straight from the receipt's line item. Trusted; goes through.
Tier 2From the merchantUsed only when a receipt has no line detail. Marked so you give it a quick check.
Tier 3Left for youConfidence too low, or nothing to go on. The account cell is left blank to assign.

The tool never writes an account it cannot back up. When the picked account does not exist in Brisken's chart of accounts, it flags the line as needing an account rather than inventing a plausible one.

The tool keeps its own records

So the work stands on its own, even if Zoho is ever switched off.

Rather than recompute from loose files every month, the tool files its inputs in three of its own stores. This is what lets the history live in the tool itself instead of only inside Zoho.

Statement table

  • One running record of every card transaction across all cards.
  • Each charge is filed under a fingerprint of its own contents, so re-downloading an overlapping period counts each charge once.
  • If a re-download has a changed amount, the tool flags the difference instead of double-storing it.

Report table

  • The Zoho Expense reports and which expense belongs to which report.
  • Carries the report's period and its per-currency totals.
  • This is what puts the report reference on every journal line.

Receipt store

  • A kept copy of each receipt image, filed under a fingerprint of the image.
  • Each one gets a stable link the journal can carry.
  • The same image is only ever stored once.
All three are optional and off by default A run only keeps these records when the settings file asks for them. A plain run writes nothing extra, and a preview run keeps nothing at all.

What you get back

A sheet to review, and a journal to import when you are ready.

The Excel review sheet

  • Every charge, its receipt, and the matched outcome side by side.
  • Rows colored by how the category was decided, so the ones that want a check stand out.
  • A separate tab lists anything the tool could not read, so nothing is silently skipped.

The Zoho Books journal

  • One balanced entry per charge: the expense on one side, the card on the other.
  • Only charges that actually matched are written; the rest wait for your review.
  • Two extra columns carry the receipt link and the report reference, on every line, so you can click straight to the proof.

The journal is a file to import. Posting it into Zoho stays a separate step that a person triggers, because a posted journal is hard to take back. The tool writes the file; it never posts on its own.

Running it

One command, one settings file.

A run is one command pointed at a settings file. The settings file names the two inputs, their column maps, and which outputs to write. Here is the command, with the preview option underneath:

expense-recon --config april.json

# preview only: run everything, print a summary, write nothing
expense-recon --config april.json --dry-run

The settings file reads like this. The store and hosting sections are the optional records from earlier; leave them out and the run still produces the review sheet and the journal.

{
  "statement": { "path": "chase-april.csv", "account_id": "chase-2838",
                 "column_map": { "transaction_date": "Date", "amount": "Amount", "vendor": "Description" } },
  "receipts":  { "path": "expense-april.csv", "source": "expense_csv",
                 "column_map": { "expense_date": "Expense Date", "amount": "Amount", "vendor": "Merchant" } },
  "store":     { "statements_path": "statements.sqlite", "reports_path": "reports.sqlite" },
  "hosting":   { "root": "receipt-store", "receipts_dir": "receipts" },
  "zoho":      { "export_path": "zoho-journal.csv" }
}

Safety and audit

Check before you keep it, and know what every past run did.

  • Preview first. The dry run does the whole pass and prints the counts without writing a file, so a month can be checked before it is kept.
  • A pre-flight check. A doctor command looks over the settings and the input files before a real run, and points at anything missing or misnamed.
  • A record of every run. When asked to, the tool logs each run and what it decided, so you can later ask what was done in a given month and compare two runs.
  • Nothing posts on its own. The journal is written as a file. Posting it into Zoho is always a deliberate, human step.
