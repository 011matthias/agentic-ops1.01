## 1. Executive Summary

This document defines the requirements for an AI-assisted expense reconciliation application intended to automate the processing, matching, classification, review, and export of business expenses into Zoho Books.

The product is intended to be developed as a commercial product for use by different companies, not only as an internal tool. The initial target is small and medium-sized businesses that currently spend significant time manually reconciling credit card statements with receipts and preparing expenses for accounting systems.

The core value proposition is:

> Reduce credit card and expense reconciliation effort from several days per month to approximately 15 minutes, while preserving configurable levels of human control, review, and approval.

The product must support both controlled/manual workflows and increasingly automated workflows. The degree of automation should not be hard-coded as a product philosophy; it should be configurable by each user or organization depending on their risk appetite, accounting policy, maturity, and trust in AI-assisted processing.

---

## 2. Product Vision

The application is not merely a receipt scanner or OCR tool. It is an AI-native expense reconciliation and bookkeeping assistant.

The system should ingest financial transaction sources, ingest receipts and invoices, extract relevant data, automatically match receipts to transactions, classify the expense using AI logic, support a review and approval process, and export or post the approved expenses into Zoho Books.

Primary product concept:

> An AI-powered expense reconciliation platform that combines document extraction, transaction matching, intelligent expense classification, receipt attachment, approval workflows, and accounting-system export.

---

## 3. Core Business Problem

Companies often have:

- credit card statements with multiple business transactions;
- receipts and invoices stored separately as photos, PDFs, emails, or files;
- personal expenses accidentally made on business cards;
- business expenses paid using personal cards and requiring reimbursement;
- missing, duplicate, or unclear receipts;
- manual classification work;
- manual upload into accounting systems;
- manual attachment of supporting documents;
- repeated reconciliation effort every month.

The product should solve this by creating a structured workflow that connects financial statement lines to their corresponding receipts, applies AI-based classification, allows user review, and prepares or performs export into Zoho Books.

## 4. Target Users

### 4.1 Initial User Type

The initial MVP can assume a single administrative user responsible for the full process:

- uploading credit card statements;
- uploading receipts;
- reviewing matches and classifications;
- correcting extracted data;
- approving records;
- exporting approved expenses to Zoho Books.

### 4.2 Future User Types

The product should be designed with future roles and authorization controls in mind.

Future roles may include:

- Admin / Finance Manager;
- Employee / Submitter;
- Reviewer;
- Approver;
- Accountant / External Advisor;
- Read-only auditor.

For MVP, only the Admin role is required, but the architecture should not block future role-based access control.

## 5. Scope Overview

## 5.1 MVP Scope

The MVP should be a browser-accessible application running on laptop/desktop.

The MVP must support:

1. credit card statement upload;
2. receipt and invoice upload;
3. OCR/data extraction from uploaded documents;
4. AI-based classification of expenses;
5. automatic matching of receipts to credit card statement lines;
6. review table/dashboard;
7. correction and approval workflow;
8. export of approved expenses to Zoho Books through file interface;
9. attachment of original or scanned receipts to the corresponding expense records, to the extent supported by the chosen MVP export method.

The MVP should not be only an Excel tool. It must be a structured application.

## 5.2 Post-MVP Release 2

The first major release after MVP should add live API integrations, especially:

- Zoho Books API integration;
- posting expenses directly into Zoho Books;
- uploading receipt attachments directly to Zoho Books;
- possibly importing statements directly from connected sources.

## 5.3 Post-MVP Release 3

The next major release should add mobile scanning:

- mobile app or mobile web interface;
- direct scan of receipts using a phone camera;
- automatic upload to the application;
- possible submitter workflow for employees.

## 9. Receipt Storage Requirement

The application must retain the uploaded receipt or scanned receipt inside the application.

The receipt file should remain linked to:

- the extracted document record;
- the matched credit card or bank statement transaction;
- the approved accounting expense record;
- the export/posting status.

For MVP, no retention period limit is required. The system can store documents indefinitely.

For future versions, document retention and deletion must consider:

- fiscal document retention requirements;
- GDPR requirements;
- user/company policy;
- minimum and maximum storage periods;
- deletion/anonymization workflows.

## 10. Required Accounting Fields

The required fields for accounting posting/export are:

1. Date;
2. Vendor;
3. Total amount;
4. Account or credit card used;
5. Currency;
6. Expense account/category to post to.

VAT is not required for the initial management-reporting use case.

### 10.1 Additional Extracted Fields

The system should extract and retain as much additional information as possible, such as:

- receipt/invoice number;
- reference number;
- address;
- payment method;
- original language text;
- line item details;
- country;
- tax/VAT information, even if not used for posting;
- merchant metadata;
- notes;
- confidence scores;
- extraction warnings.

### 10.2 Reference Field Logic

Receipt number, invoice number, or similar identifying document number should be mapped to the reference field where available.

### 10.3 Description Field Logic

Line item details should not be posted as separate accounting lines for MVP. They may be consolidated into the description or additional information field, subject to available character limits.

The total receipt amount is the amount to be posted into accounting.

## 11. VAT / Tax Handling

VAT does not need to be accounted for in the MVP because the initial purpose is management reporting.

However, the system should still extract VAT/tax information when visible and store it as supporting metadata.

Future versions may require:

- VAT rate separation;
- German VAT handling;
- mixed VAT receipts;
- tax code mapping;
- country-specific tax treatment.

Open question for future specification:

- Should VAT extraction be visually shown in the review table even though it is not posted in MVP?

## 12. Languages

The system should recognize receipts in multiple languages, including at least:

- German;
- English;
- Portuguese.

The system should be able to translate relevant extracted information into English if required for Zoho Books fields or management reporting.

Original language information should be preserved where useful, especially in the description or document metadata.

## 13. AI Classification Logic

The system must use AI logic to classify expenses dynamically.

The user specifically does not want a simple static vendor assignment table as the main intelligence mechanism.

The classification logic should consider:

- vendor name;
- transaction description;
- receipt line items;
- amount;
- currency;
- country/location;
- historical user corrections;
- organization-specific chart of accounts;
- context from the statement line;
- uploaded document content.

Example assumptions:

- Restaurant vendors are usually Meals & Entertainment.
- Electronics stores such as Best Buy are often Office Equipment or Office Electronics.
- However, line items may override vendor-level assumptions.

The classification engine should produce:

- suggested expense account/category;
- confidence score;
- explanation/reasoning summary suitable for review;
- possible alternative category if uncertain;
- warning flag if classification is ambiguous.

### 13.1 Learning from Corrections

Future versions should learn from user corrections.

For MVP, the system may store corrections but does not necessarily need to train a model. However, the architecture should allow future improvement based on correction history.

---

## 14. Configurable Automation Philosophy

The product must support different levels of automation.

This is not a fixed product decision. It is a usage/configuration decision controlled by each company or user.

The product should support:

1. fully manual review workflow;
2. AI-assisted workflow with human approval;
3. semi-automated approval based on confidence thresholds;
4. fully automated posting for high-confidence records.

The organization should be able to define control policies such as:

- always require approval;
- auto-approve only above a confidence threshold;
- auto-approve certain low-risk categories;
- always review high-value transactions;
- always review personal/business ambiguity;
- always review missing receipt cases;
- allow admin override.

For MVP, the default should be review-before-export.

Future versions should allow configurable automation thresholds.

## 15. Matching Engine

The matching engine is a critical component of the product.

It must automatically match uploaded receipts/invoices to credit card statement lines.

### 15.1 Matching Criteria

Matching should consider:

- amount;
- date;
- vendor name similarity;
- currency;
- payment method;
- receipt timestamp;
- statement description;
- document reference;
- card/account used;
- possible settlement date differences.

### 15.2 Matching Date Logic

The system must account for common date differences:

- purchase date vs posting date;
- receipt date vs statement date;
- timezone differences;
- weekend/bank processing delays.

### 15.3 Matching Outcomes

The system should classify matches as:

- exact/high-confidence match;
- probable match;
- possible match requiring review;
- no match found;
- duplicate/ambiguous match;
- multiple receipts for one transaction;
- one receipt possibly matching multiple transactions.

### 15.4 Confidence Score

Every match should have a confidence score.

The score should be visible in the review table.

Suggested levels:

- High confidence: can be auto-approved if policy allows;
- Medium confidence: review required;
- Low confidence: manual matching required;
- Conflict: user must resolve.

Open question:

- Define exact thresholds, e.g. high confidence >= 95%, medium 75-94%, low below 75%.

## 17. Personal vs Business Expense Handling

The system must support separation of:

1. personal expenses made on a business card;
2. business expenses made on a personal card requiring reimbursement;
3. normal business expenses made on business payment methods.

There are specific fields in Zoho Books that may support this, but they need to be specified later.

For MVP, the system should include flags or fields such as:

- Business expense;
- Personal expense on business card;
- Reimbursable business expense paid personally;
- Do not export;
- Export as reimbursement;
- Needs accounting review.

Open question:

- Define exact Zoho Books fields and posting logic for personal/business/reimbursement cases.

---

## 18. Duplicate Detection

The system should detect potential duplicates.

Duplicate detection should consider:

- identical receipt image hash;
- same vendor;
- same date;
- same amount;
- same reference number;
- similar OCR text;
- multiple uploads of the same file;
- same transaction line matched to multiple receipts.

The system should not automatically delete duplicates without user review.

Suggested behavior:

- flag duplicate suspected;
- show duplicates side by side;
- allow user to merge, ignore, or confirm separate documents.

---

## 19. Multi-Receipt and Split Cases

The system should eventually support:

- multiple receipts matching one statement transaction;
- one receipt split across multiple accounting categories;
- one transaction split into business and personal portions;
- one transaction with multiple cost centers/projects;
- tips or service fees causing differences between receipt total and card charge.

For MVP, this can be simplified.

Open question:

- Should MVP support split expenses, or should such cases be manually edited/handled outside the system initially?

---

## 20. Currency Handling

The MVP must capture the currency.

The system should store:

- receipt currency;
- statement currency;
- posted/accounting currency if different;
- amount on receipt;
- amount on statement;
- exchange rate if available;
- difference/warning if amounts differ.

Open questions:

- What is the company base currency?
- Should the system use card statement amount as the accounting amount even when the receipt is in another currency?
- Should exchange rates be imported, calculated, or simply stored from the statement?

## 21. Zoho Books Export / Integration

### 21.1 MVP Export

The MVP should use a file interface for Zoho Books.

The application should generate a Zoho-compatible CSV or Excel file for approved expenses.

The export should include at least:

- Date;
- Vendor;
- Expense Account;
- Amount;
- Currency;
- Paid Through / Account or Credit Card;
- Reference Number;
- Description;
- Notes;
- attachment reference if supported by the import method.

### 21.2 Receipt Attachment Requirement

The original or scanned receipt must be linked to the expense and uploaded into Zoho Books.

Open issue:

- Confirm whether the chosen Zoho Books file import method supports receipt attachment import directly.
- If not, MVP may need a workaround: export data plus file package, or use API earlier for attachments.

### 21.3 Future Zoho API Integration

Post-MVP, the system should connect live to Zoho Books API to:

- create expenses;
- upload attachments;
- retrieve chart of accounts;
- retrieve vendors;
- retrieve bank/credit card accounts;
- retrieve custom fields;
- update posting status;
- handle API errors;
- prevent duplicate posting.

## 22. Chart of Accounts / Categories

The application must allow the admin user to define or import the expense accounts/categories used for classification.

For MVP, the user should be able to:

- manually enter categories;
- upload category list;
- edit categories;
- activate/deactivate categories;
- map AI classification outputs to Zoho Books expense accounts.

Future API integration should allow direct import of Zoho Books chart of accounts.

The AI should classify based on the available category list, not invent categories that do not exist, unless it marks them as suggestions requiring mapping.

## 24. AI/OCR Processing Pipeline

Suggested pipeline:

1. Upload document.
2. Store original file.
3. Run OCR/document extraction.
4. Detect language.
5. Extract structured fields.
6. Normalize extracted values.
7. Compare receipt with transaction records.
8. Generate match candidates.
9. Generate AI classification.
10. Assign confidence scores.
11. Create review record.
12. User reviews/edits/approves.
13. Export or post approved record.
14. Update status and store output logs.

## 25. Non-Functional Requirements

### 25.1 Accuracy

The product must prioritize correctness and transparency over blind automation.

Where information is unclear, the system should mark it as uncertain rather than inventing data.

### 25.2 Performance

The MVP should be able to process at least a typical monthly credit card statement and corresponding receipts without requiring manual one-by-one handling.

Open question:

- Define expected monthly transaction/document volume for MVP testing.

### 25.3 Security

The system will process financial documents and potentially personal data.

Security requirements should include:

- authenticated access;
- encrypted file storage;
- encrypted transport;
- secure API key management;
- restricted access to organization data;
- separation of customer organizations in future multi-tenant version.

### 25.4 GDPR / Privacy

Future commercial use must consider GDPR requirements.

MVP should already avoid poor data handling practices.

Consider:

- lawful basis for processing;
- document deletion;
- user access rights;
- data export;
- data minimization;
- retention policies;
- third-party processors for OCR/AI.

### 25.5 Auditability

For MVP, full audit logging is not required.

However, future design should allow:

- tracking who changed what;
- when a category was changed;
- who approved;
- what was exported;
- API posting logs;
- AI suggestions vs final human decisions.

## 26. Suggested Technical Architecture

### 26.1 Frontend

Recommended:

- React or Next.js;
- browser-based application;
- data table/grid component with strong filtering and inline editing;
- document preview panel.

### 26.2 Backend

Recommended:

- Python FastAPI;
- REST API;
- background job processing for OCR/AI tasks.

Python is preferred because OCR, document processing, AI orchestration, and reconciliation logic are easier to implement and maintain.

### 26.3 Database

Recommended:

- PostgreSQL.

### 26.4 File Storage

Recommended:

- AWS S3;
- Azure Blob Storage;
- or equivalent secure object storage.

### 26.5 OCR / Document Intelligence

Options:

- Azure Document Intelligence;
- Google Document AI;
- AWS Textract;
- hybrid approach using OCR plus LLM extraction.

### 26.6 AI Layer

Use an LLM for:

- field extraction validation;
- classification;
- reasoning over line items;
- matching support;
- ambiguity detection;
- explanation generation.

The system should keep structured outputs and confidence values rather than only natural language responses.

### 26.7 Background Jobs

Use background processing for:

- OCR;
- AI extraction;
- statement import parsing;
- matching;
- export generation;
- future API posting.

Possible tools:

- Celery;
- RQ;
- cloud-native queues;
- worker services.

The system should clearly flag:

- missing receipt;
- duplicate receipt;
- ambiguous match;
- receipt amount differs from statement amount;
- receipt currency differs from statement currency;
- date mismatch outside tolerance;
- vendor mismatch;

## 30. MVP Success Criteria

The MVP is successful if it can:

1. import a monthly credit card statement;
2. upload a batch of receipts;
3. extract core receipt data with acceptable accuracy;
4. automatically match most receipts to statement lines;
5. classify expenses using AI logic based on the available categories;
6. allow efficient review and correction in a single table;
7. export approved records to a Zoho Books-compatible file;
8. preserve links between transactions, receipts, and exported expenses;
9. significantly reduce the manual reconciliation workload.

Business success target:

> Reduce monthly credit card reconciliation effort from several days to approximately 15 minutes.

## 34. Key Product Principles

1. The product is not just OCR.
2. The main value is reconciliation and classification.
3. AI should assist intelligently, but the organization controls the automation level.
4. Users must be able to review, correct, and approve.
5. The receipt must stay linked to the transaction and accounting record.
6. The system should not invent missing data.
7. The system should clearly show uncertainty.
8. The review table is the core user experience.
9. Zoho Books Expenses are the first accounting target.
10. The architecture should allow future APIs, roles, mobile scanning, and broader accounting integrations.

## 35. Initial One-Sentence Developer Brief

Build a browser-based AI-assisted expense reconciliation application that imports credit card statements, uploads and stores receipt files, extracts receipt data, automatically matches receipts to statement transactions, dynamically classifies expenses using AI against a configurable chart of accounts, provides a review and approval table, and exports approved expense records with receipt linkage for Zoho Books, with future readiness for Zoho API integration, mobile receipt scanning, multi-user roles, and configurable automation controls.
