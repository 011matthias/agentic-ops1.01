#14 -- Hero-API Smoketest (Runbook)

Zweck: Schneller Nachweis, dass die neu generierten Hero-API-Tokens (3672 Sabine, 3785 Sammelbearbeiter) gegen den Live-Endpoint funktionieren, bevor der Friday-Walkthrough mit Raphael startet. Entdeckt Auth-Fehler in < 30 Sekunden statt mitten im Meeting.

Status heute (2026-04-15): Blocker -- Tokens noch nicht neu generiert. Sobald Raphael das Self-Service-Feld in der Hero-UI (Schnittstellen > API) durchgeklickt hat, laeuft dieses Runbook in einem Befehl durch.

Stand 2026-05-03 · 9/10 Hero-Szenarien live · W2-10 deferred zu n8n · Auto-Buy aktiv

Endpoint (verifiziert)

https://login.hero-software.de/api/external/v9/graphql

Alle 10 Hero-Blueprints senden HTTP-POSTs an diesen Endpoint. Der Token geht im Authorization: Bearer <token> Header -- in Make verwaltet als auth-Parameter auf http:ActionSendDataAPIKeyAuth-Modulen.

Zwei Tokens, zwei Scopes

Auth-ID Label in Make Szenarien Typ
3672 Sabine Wimmer (personalisiert) #3, #5, #7, #8, #9, #10 User-Token
3785 Sammelbearbeiter HERO #1, #2, #4, #6 Service-artig

Evidence: siehe 12-cross-reference.md + audit-2026-04-15.json (Parameter auth pro http-Modul).

Runbook (drei Befehle)

Schritt 1: Token regenerieren (Raphael)

In Hero UI: Schnittstellen > API.

  • Token 3672 erneuern, neuen Wert in 1Password-Safe ablegen (Slot hero-sabine-3672)
  • Token 3785 erneuern, Slot hero-sammel-3785
  • Alte Tokens sind laut Hero nicht mehr sichtbar -- die Neu-Generierung ist die einzige Option

Schritt 2: Tokens in shell-env laden (Nico)

export HERO_TOKEN_SABINE="$(op read op://agentic-ops/hero-sabine-3672/token)"
export HERO_TOKEN_SAMMEL="$(op read op://agentic-ops/hero-sammel-3785/token)"

(1Password-CLI op. Alternativ beide Werte per WhatsApp-Voice und manuell in .env.warme-wimmer legen -- aber NICHT in Git!)

Schritt 3: Smoketest ausführen (Nico)

uv run hero-api-smoketest.py --out api-smoketest-$(date +%F).md

Erwarteter Exit-Code 0 = beide Tokens valide, Entity-Fetch erfolgreich. Exit 1 = Auth-Fail; Exit 2 = Endpoint OK, aber GraphQL-Errors (z.B. Scope-Restriktion).

Der Report api-smoketest-YYYY-MM-DD.md wird von Nico lokal abgelegt und dient als Beleg für die Walkthrough-Praesentation am 2026-04-17.

Was der Smoketest prüft

  1. Endpoint reachable: TCP + TLS zum Hero-Server
  2. Auth valid: Authorization: Bearer wird akzeptiert (kein HTTP 401/403)
  3. Viewer-Query: GraphQL-Schema antwortet mit dem User-Context des Tokens (viewer.id, viewer.name)
  4. Entity-Fetch: project_matches(limit: 1) liefert mindestens 1 Eintrag -- beweist Read-Scope auf Projekt-Daten

Die Entity-Fetch-Query ist mit Absicht schlank gehalten: reine Leseoperation, keine Mutation, kein Risiko Produktiv-Daten zu verändern.

Bei Fehler

Symptom Diagnose Nächster Schritt
HTTP 401/403 Token falsch, abgelaufen oder falsch kopiert Token erneut via Hero UI generieren, sicherstellen dass kein Leerzeichen im Token
errors: ["Cannot query field ... on type ..."] GraphQL-Schema-Änderung auf Hero-Seite seit Export 2026-04-09 Vor Walkthrough mit Raphael klaeren, ob Schema-Version v9 noch aktuell ist
Timeout / connection refused Hero-Server nicht erreichbar Hero-Support-Status prüfen, Meeting ggf. verschieben
Entity-Fetch project_matches: [] Scope korrekt, aber Token hat keine Projekt-Leseberechtigung Kritischer Blocker für #1, #4, #7-10 -- Raphael bitten Scope auszuweiten

Zeitbudget

Smoketest wurde so gebaut dass er komplett in unter 30 Sekunden durchlaeuft (2 HTTP-Roundtrips pro Token, 4 insgesamt). Passt vor jeden Walkthrough, jeden Build-Session.

Verankerung im Build-Pfad

Nach erfolgreichem Smoketest sind folgende WW-Make-Account-Arbeiten unblockiert (aus infrastructure.yaml > make.pending_connections):

  • 20 Connection-Slots können verdrahtet werden (inkl. Hero-API-Tokens als Connection-Credentials)
  • 3 Data-Store-Rebinds
  • 5 Webhook-URL-Pastes

Ohne Smoketest-Pass bleibt der Build blockiert -- wir importieren keine Szenarien mit Platzhalter-Tokens in ein Pro-Abo.
