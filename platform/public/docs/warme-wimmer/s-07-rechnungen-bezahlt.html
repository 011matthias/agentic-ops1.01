Was tut es (Business-Outcome)

Schedule-Szenario (Polling). Sucht alle Projekte, die in den Status 317169 (Tagesgeschäft) oder 368546 (Nacharbeiten) stehen — also auf Rechnungs-Zahlung warten.

Für jedes Projekt: wenn alle Rechnungsdokumente (document_type_ids 952733, 737664, 688377, 688386) keine offene Buchung (status != "open") mehr haben, wird das Projekt auf 317171 (Tagesgeschäft) bzw. 368548 (Nacharbeiten) = "Abgeschlossen" gesetzt.

LexOffice-Relevanz: laut Raphael interessant — Buchungsstatus kommt aus LexOffice. Deep-Dive erforderlich, wie die Schnittstelle aussieht.

Trigger

  • Typ: Schedule (Polling) — Intervall im Blueprint nicht definiert (scheduling: null), wird bei Import im UI oder per MCP gesetzt
  • Klaus-PDF-Realdaten: Täglich 05:00 Uhr, 30 Ausführungen/Monat, 128 Ops/Monat (extrem günstig). Zero Errors in HERO-Produktion.

Branching-Logik

GraphQL-Query (Auth 3672) liefert zwei benannte Query-Blöcke: - Tagesgeschäft (step 317169) mit customer_documents + booking.status - Nacharbeiten (step 368546) mit customer_documents + booking.status

Router mit 2 Routen (kein Router-Filter — jede Route hat eigenen Feeder + Filter):

Route Filter Aktion
R0 Tagesgeschäft customer_documents ≠ 0 AND alle booking.status ≠ "open" Status → 317171
R1 Nacharbeiten customer_documents ≠ 0 AND alle booking.status ≠ "open" Status → 368548
