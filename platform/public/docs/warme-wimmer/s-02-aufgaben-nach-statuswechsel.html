SZENARIO 2 — AUFGABEN NACH STATUSWECHSEL

Hero-Trigger: WatchProjects (alte Hero-App hero-software)
Webhook-ID: 55803  |  Auth: 3785 (Sammelbearbeiter)

Aufgaben-Zuweisung:
  target_user_id: 270612 (hardcoded = Sabine als Sammelbearbeiter)

Status-Filter (text:contain:ci, ODER-verknuepft):
  - Angebotserstellung
  - Materialbestellung
  - Terminiert
  - Erledigt

Faelligkeit:
  Klaus-PDF (2026-04-15) sagt: Sekundaer-Aufgaben "Angebot angenommen"
  und "Material angekommen" haben KEIN Faelligkeitsdatum.
  Deployed-Blueprint setzt aber +7 Tage. DRIFT — mit Klaus klaeren.

BEKANNTE SCHWAECHEN:
- Hardcoded user_id 270612: faellt Sabine aus, gehen Aufgaben ins Leere
- Status-Filter auf Namen statt IDs: Umbenennung bricht alles
- search_partner GraphQL-Call wird ausgefuehrt aber nirgends genutzt
  (Dead Code aus altem Design, vermutlich war geplant target_user_id
  dynamisch aus search_partner zu setzen)
- Kein Dedup: Status-Wechsel hin und her -> Aufgaben mehrfach angelegt

GEPLANTE AENDERUNGEN IN N8N-MIGRATION:
- Status-Filter auf Status-IDs umstellen
- target_user_id dynamisch aus Projektzuweisung lesen statt hardcoded
- Dead-Code search_partner entfernen oder Result wirklich nutzen
- Dedup ueber Aufgaben-Titel + Projekt-ID
- Faelligkeitsdatum-Drift zu Klaus klaeren

Was tut es (Business-Outcome)

Spiegelbild zu #1: Sobald sich ein Projektstatus ändert, werden automatisch die zugehörigen Tasks angelegt, die in diesem Status zu erledigen sind. Ziel ist, dass Sabine nie manuell eine Aufgabe anlegen muss — jeder Status hat ein Task-Paket, das hier scripted angelegt wird.

Beispiel: Projekt rutscht in "Angebotserstellung" → Szenario legt Task "Angebot schreiben" (fällig in 7 Tagen) und Task "Angebot angenommen" (offen) für User 270612 an.

Trigger

  • Typ: Event (hero-software:WatchProjects, alte Hero-App-Variante)
  • Hook-ID: 55803
  • Auth: 3785 (Sammelbearbeiter)

Branching-Logik

Top-Filter am Partner-Lookup prüft, dass Status einer von vier Werten ist. Danach Router mit 4 Routen, jede triggert eine GraphQL-Mutation update_task:

Status Angelegte Tasks Fälligkeit
Angebotserstellung "Angebot schreiben" + "Angebot angenommen" +7 Tage / siehe DRIFT unten
Materialbestellung "Material bestellen" + "Material angekommen" +7 Tage / siehe DRIFT unten
Terminiert "Terminbestätigung eingegangen" +7 Tage
Erledigt "Rechnung kann gestellt werden" +7 Tage

[DRIFT — Klaus klären 2026-04-19+] Klaus-PDF (2026-04-15) sagt explizit: Sekundär-Tasks Angebot angenommen und Material angekommen haben kein Fälligkeitsdatum. Deployed Blueprint setzt aber +7 Tage. Test-Bench-Replay bestätigt: Blueprint-Verhalten ist +7d. Frage an Klaus: PDF richtig (entfernen) oder Blueprint richtig (PDF korrigieren)? Wenn PDF stimmt: 5-Min-Fix im Blueprint (due_date-Mapper auf null). Quelle: blueprint-pdf-drift.md Finding 1 (HIGH).

Risiko-Bewertung

Mid-High. Ausfall = neue Projekte bekommen keine Folge-Tasks → Sabine merkt nicht automatisch, was als Nächstes zu tun ist. Feedback-Schleife mit #1 ist gebrochen (Tasks fehlen, die erledigt werden müssten, damit #1 greift).

Rote Fahnen / Altlasten

  • Hardcoded user_id 270612 in allen Routen. Wenn Sabine ausfällt / kündigt / anderer Projektverantwortlicher → Tasks gehen ins Leere.
  • Partner-Lookup (Modul 4) wird ausgeführt, aber Ergebnis nicht im update_task verwendet — dead code oder Legacy.
  • Alte Hero-App-Variante (hero-software), nicht die neue (app#herosoftwareintern-ba9lus).
  • Kein Dedup: Wenn Status zwischen den vier Werten hin und her springt, werden jedes Mal dieselben Tasks doppelt angelegt.
