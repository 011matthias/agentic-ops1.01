Annotations

SZENARIO 6 — PROJEKTERINNERUNG 1 TAG NACH TERMIN

Trigger: app#herosoftwareintern-ba9lus:WatchAppointments
Webhook-ID: 55916  |  Connection: 63756  |  Auth: 3785

Wiedervorlage-Datum (maturity_date):
  Berechnet aus end-date + addDays 1 + Zeit "07:00:00+00:00"
  UTC-Zeit -> Lokal entspricht 09:00 Sommer / 08:00 Winter

Filter (UND-verknuepft auf m2):
  category.name == "Umsetzung"     ODER
  category.name == "Aushang notwendig"
  UND project_match_id != 0

Status-Switch nur fuer Tagesgeschaeft (TG):
  type.id == 25153 (TG)
  AND step_id == 317167 (Zu verplanen)
  -> set 317168 (Terminiert)

NA hat KEIN Status-Switch in diesem Szenario.

WIEDERVORLAGE WIRD BEIM STATUS-WECHSEL GELEERT:
  Bei jedem UpdateProjectStatus erzeugt Hero eine NEUE
  current_project_match_status-Row mit leerem maturity_date.
  Das ist Standard-Hero-Verhalten, kein Bug.

BEKANNTE SCHWAECHEN:
- Status-Switch nur fuer TG, NA wird ignoriert (Asymmetrie)
- Hardcoded Uhrzeit 07:00 UTC -> bricht bei Zeitumstellung leicht
- text:equal auf category.name "Umsetzung" -> bei Umbenennung
  in "Umsetzungstermin" greift's nicht mehr
- Termin-Verschiebung loest WatchAppointments mehrfach aus,
  maturity_date wird mehrfach (gleich) gesetzt — keine echte
  Schwaeche, aber unnoetiger Traffic

GEPLANTE AENDERUNGEN IN N8N-MIGRATION:
- Kategorie-IDs statt Namen (254476 = Umsetzung, 254478 = Aushang)
- Lokal-Zeit statt UTC fuer maturity_date
- Auch NA-Pendant einbauen (oder bewusst entscheiden ohne)
- Doppel-Trigger-Schutz (nur eindeutige Termine verarbeiten)

Was tut es (Business-Outcome)

Wenn ein Kalendertermin der Kategorie "Umsetzung" oder "Aushang notwendig" angelegt / verändert wird, setzt dieses Szenario das Projekt-Fälligkeitsdatum (maturity_date) auf Termin+1 Tag.

Das bewirkt, dass das Projekt am Tag nach der Umsetzung automatisch wieder "oben aufschlägt" im HERO-Dashboard (Erinnerungsfunktion). Zusätzlich wird der Projektstatus von 317167 (Terminiert offen) auf 317168 (Terminiert mit Termin) gehoben, wenn die Bedingungen stimmen.

Trigger

  • Typ: Event (app#herosoftwareintern-ba9lus:WatchAppointments, neue Variante)
  • Hook-ID: 55916
  • Connection: 63756

Branching-Logik

  • Pre-Filter am HTTP-Modul 2: (category.name = "Umsetzung" OR "Aushang notwendig") AND project_match_id ≠ 0
  • HTTP-GraphQL-Mutation (Auth 3785): update_project_match mit maturity_date = {termin.end + 1 Tag}T07:00:00+00:00
  • GetProject (conn 63756): lädt Projekt zum Statuscheck
  • Router-Route "Tagesgeschäft" (type.id = 25153 AND step_id = 317167) → UpdateProjectStatus auf 317168

Modul-Inventar (Node-by-Node)

Jeder Eintrag = ein Modul im Make-Szenario. Einrückung = verschachtelt in Router-Route.

  • Modul 1: HERO Webhook: Termin erstellt/aktualisiert
  • Modul 2: HTTP Request (API-Key Auth) | Filter vorhanden (4 Bedingungen)
  • Modul 5: HERO API: Projekt laden (GraphQL)
  • Modul 4: Router (Verzweigung)
  • Route 0 (Route 0):
    • Modul 3: HERO API: Projektstatus setzen | Filter vorhanden (2 Bedingungen)
