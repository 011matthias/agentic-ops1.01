Solution Architecture

Five Pipelines, One Engine

Each pipeline is a self-contained n8n workflow that shares a common company registry, storage layer, and error handling infrastructure.

Pipeline 1: Web Scraping Dispatcher

1
Scheduled Batch Dispatcher
Reads company registry, dispatches scraping jobs in controlled batches
Schedule Trigger → Google Sheets → Filter (due for scrape) → Split in Batches → Execute Sub-Workflow → Update Last Scraped

The dispatcher runs on a schedule (configurable: daily, weekly, or on-demand). It reads your Google Sheets company registry, filters for companies due for a scrape, splits them into batches of 10-20 to respect rate limits, and dispatches each batch to the scraper sub-workflow.

Why a dispatcher? If one company's scrape fails, it does not block the other 299. Each batch runs independently with its own error handling. Failed companies get logged and retried on the next run.

Pipeline 2: Modular Document Scrapers

2
AI-Powered Link Extraction
Per-company scraping with document classification and cloud storage
Receive Company URL → HTTP Request → Claude: Extract Links → Dedup Check → Download Documents → Cloud Storage

For each company, the scraper fetches the investor relations page via HTTP Request, passes the raw HTML to Claude API for link extraction and classification (Annual Report, Quarterly Filing, Investor Presentation, etc.), deduplicates against previously downloaded documents, downloads new files, and stores them in cloud storage organized by ticker symbol.

Honest note: Browser API requirement

n8n does not have a native headless browser. For JavaScript-rendered investor relations pages (React, Angular, or heavy SPA sites), we use an external browser API service like ScrapingBee, Bright Data, or Apify. This is actually the production-grade approach: these services handle CAPTCHA solving, proxy rotation, and browser fingerprinting better than a self-hosted Puppeteer instance. The trade-off is a per-request cost (typically $0.001-0.01 per page). For 300+ companies scraped weekly, expect $5-30/month in browser API costs depending on how many sites require JS rendering.

Pipeline 3: Thesis Synthesis

3
Multi-Document Analysis
Detects new analysis files, synthesizes against existing thesis
File Watcher → Fetch Thesis Files (4 docs) → Claude: Synthesize → HITL Email → Markdown Append

When a new analysis file appears in your cloud storage (e.g., a freshly scraped annual report), the file watcher triggers this pipeline. It fetches the existing thesis documents for that company (Core Thesis, Financial Model, Risk Assessment, Catalyst Tracker), passes everything to Claude with a synthesis prompt, and generates a proposed update.

The proposed update is sent to HITL approval (Pipeline 5) before any file is modified. On approval, a Code node reads the target markdown file, identifies the correct section using regex, and appends the new content without overwriting existing analysis.

Pipeline 4: News Intelligence Filter

4
Relevance-Scored News Monitoring
Multi-source news scraping filtered against your investment thesis
Schedule (Daily) → Tavily / AlphaVantage / SerpAPI / RSS → Merge + Dedup → Claude: Score Relevance → Filter (score > threshold) → JSON Digest

Runs daily. Fetches news from multiple sources: Tavily (AI-optimized web search), AlphaVantage (financial news API), SerpAPI (Google News results), and RSS feeds (configurable per company). Results are merged, deduplicated by URL, then passed to Claude with the company's Core Thesis for relevance scoring.

Each article gets a relevance score (0-100) and a classification: Material Deviation (contradicts thesis), Thesis Confirmation (supports thesis), New Information (not covered by thesis), or Noise (irrelevant). Articles scoring above your configurable threshold are included in the daily digest. Material deviations trigger HITL review (Pipeline 5).

Pipeline 5: HITL Email Approval

5
Human-in-the-Loop Gate
Nothing modifies your core files without explicit approval
Approval Request → Generate Email (HTML) → Send Email → Wait Node → Webhook (Approve/Reject) → Execute Action

This is the safety layer. Whenever Pipeline 3 (Thesis Synthesis) or Pipeline 4 (News Filter) produces an update that would modify a core file, it routes through this approval flow instead of writing directly.

How It Works

  1. Email generation: An HTML email is generated showing the proposed change (what will be modified, before/after preview, source references)
  2. Approve/Reject buttons: Two buttons in the email, each linking to a unique webhook URL with a signed token (prevents unauthorized approvals)
  3. Wait node: The n8n execution pauses at a Wait node, holding state until the webhook fires
  4. Webhook callback: Clicking Approve or Reject in the email hits the webhook, which resumes the paused execution
  5. Action: On Approve, the markdown append runs. On Reject, the proposed change is logged but not applied
Honest note: Wait node mechanics

n8n's Wait node pauses an execution and resumes it when a webhook fires. This is not a native approval queue with a UI dashboard. You approve or reject via email buttons. The upside: it works everywhere (phone, desktop, any email client). The downside: if the n8n instance restarts, paused executions resume from their saved state but the wait timeout resets. We configure a 7-day timeout with a fallback reminder email at day 3.

Shared Infrastructure

All five pipelines share these components. Building them once means consistent behavior across the entire system.

∞
Common Components
Registry, storage, error handling, and logging

Company Registry (Google Sheets)

Single source of truth for all 300+ companies. Columns: ticker, company name, IR page URL, site type (static/JS/PDF), last scraped date, scrape frequency, thesis file paths, news sources. Both the dispatcher (Pipeline 1) and news filter (Pipeline 4) read from this same sheet.

Cloud Storage (Organized by Ticker)

Folder structure: /{ticker}/documents/, /{ticker}/thesis/, /{ticker}/news/. All pipelines write to the same storage with consistent naming. Compatible with Google Drive, S3, or any cloud storage n8n supports.

Error Handling

Every pipeline has an Error Trigger node that catches failures and logs them to a dedicated error sheet. Fields: timestamp, pipeline name, company ticker, error message, input data. Failed items are automatically queued for retry on the next run. After 3 consecutive failures for the same company, it is flagged for manual review.

Execution Logging

Every pipeline execution logs: start time, end time, items processed, items succeeded, items failed, duration. This feeds a simple operations dashboard (a Google Sheet with pivot tables) so you can monitor pipeline health at a glance.
