Phase 2: Phased Migration

Scenarios get migrated in dependency order. Independent scenarios go first. Anything that depends on another scenario waits until its dependencies are confirmed working in the new account.

Webhook URL cutover

This is the part that requires your sysadmin. When a scenario is webhook-triggered, the inbound URL changes when it moves to a new Make.com organization. The old URL stops working the moment the old scenario is deactivated.

How we'll handle this together

I'll prepare a cutover document for each webhook: the old URL, the new URL, the source system where it needs updating, and a test payload to confirm it's firing correctly. Your sysadmin updates the source (usually Hero Software or a server config). I confirm the new scenario received the test event. Then we deactivate the old one. For non-webhook scenarios, there's no coordination needed.

Phase 3: Parallel Validation

Where possible, I'll keep the old scenarios running alongside the new ones for a short period. This gives us a real-world confirmation that the migrated versions produce the same outputs before the old account is decommissioned.

3
Validation Approach
Week 4

Not every scenario can run in parallel. Anything that writes to LexOffice or sends emails would create duplicates. For those, I'll run manual test payloads through the new scenario and compare outputs against what the old one would have produced.

  • ✓Run read-only scenarios in both accounts simultaneously and compare outputs
  • ✓Use test mode for write operations (invoices, emails) to avoid duplicates
  • ✓Monitor Make.com execution logs for errors, timeouts, incomplete runs
  • ✓Check Hero-to-LexOffice data consistency on a per-record basis

Error notification routing

After migration, you need to know immediately if something fails. I'll configure error notification routing before the old account is shut down, so there's no gap in visibility.

⚠
Execution failure alerts

📈

Track monthly operation usage against your Make.com plan. Alert when approaching the limit so there are no surprise pauses mid-month.
📋

🔒
Connection health checks
Periodic test runs on each API connection to catch token expiry or auth issues before they block production scenarios.
When we know the migration is done

The old account gets decommissioned after all scenarios have passed validation, error routing is confirmed, and your team has signed off on at least one full business day of clean execution logs. There's no fixed date for this. It happens when the evidence says it's safe.

Phase 4: Ongoing Ownership

Migration is the start, not the end. Your scenarios will need changes as Hero Software adds statuses, Mailgun templates get updated, or your team's workflows evolve. I'll handle those as they come up.

4

What I won't do

I won't hand off a scenario map and disappear. I've seen that approach create problems three months later when something breaks and nobody knows why it was built that way. Every change I make gets documented inside Make.com (scenario names, module notes, data store descriptions) so the account stays readable, not just functional.

German business context

I'm based in Germany. I know how Hero Software is used in German HVAC and energy businesses. I know LexOffice's GoBD requirements. I've worked with German sysadmins before. You won't be explaining your context from scratch every time something comes up.
