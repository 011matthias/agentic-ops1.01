Technical questions about how we handle the hard parts, process questions about how we work, and availability.

Technical Questions

What happens if Claude returns invalid JSON?

An error router module catches parse failures before they reach any downstream module. The raw Claude response gets logged, and the scenario retries with an explicit JSON instruction added to the prompt. After 2 retries, the scenario logs a structured failure record and moves to the next client in the iterator.

There are no silent failures. Every failure produces a log entry with the client name, the scenario step that failed, and the raw response that caused it. You can see exactly what went wrong and why.

How do you handle API rate limits across multiple clients?

The client iterator includes sleep modules between each client pass. Each ad platform has different limits: Google Ads allows roughly 1,500 requests per day, Meta's limits vary by endpoint and account tier. We track usage against those thresholds and throttle the iterator accordingly.

Rate limit errors (HTTP 429) are caught separately from general API errors. When one hits, the scenario waits and retries that specific client rather than skipping them. Client N failing doesn't affect client N+1.

Can guardrails be adjusted per client?

Yes. The guardrail thresholds - things like budget ceiling percentage or the data freshness threshold - are stored as columns in the KB config tab, one per client row. Changing a client's limit means editing one cell.

What's not configurable per client is the guardrail module itself. The conditional check in Make.com is hard-coded and applies universally. The threshold it checks against is what varies. This is intentional - a configurable guardrail module would mean a determined prompt could eventually route around it. The hard check stays structural.

Process Questions

What if a scenario needs changes after delivery?

The first two weeks after each phase completion cover bug fixes at no additional cost. A bug means the scenario doesn't do what its spec says it should do. If you want new behavior added or existing behavior changed, that's a change request billed at the agreed hourly rate.

We document the spec for each scenario before building it, so there's a clear reference for what "working correctly" means. That makes the distinction between a bug and a change request unambiguous.

How do you handle the transition from Phase 1 to Phase 2?

Phase 1 scenarios keep running throughout Phase 2. We don't pause or rebuild anything. Phase 2 scenarios are built in parallel and connected to Phase 1 outputs as they're ready. The connection points are designed in Phase 1 to accept Phase 2 inputs, so there's no retrofit work needed.

The phase-level guardrails that control what's allowed to execute remain in place throughout. Phase 2 scenarios don't bypass Phase 1 guardrails - they add their own on top.

What documentation do I get?

For each scenario: the environment variables it uses, the webhook URLs it exposes or calls, a full inventory of API connections with endpoint details, the blueprint JSON export, and the test results from the delivery gate. All of this goes into a shared tracking document that's updated at every weekly check-in.

At phase completion, we do a full review pass to make sure the doc is accurate against what's actually deployed. The goal is that another developer could pick this up without needing us to explain how it works.

Have you built multi-client Make.com systems before?

Yes. We've built and maintained 10+ production Make.com scenarios for a single client covering multi-system orchestration across databases, email platforms, and spreadsheets. We also use Claude API in our own automation pipeline for proposal generation and client communications, so we've debugged the JSON parsing and retry behavior in production, not just in test environments.
