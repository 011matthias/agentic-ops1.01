Phase 1: Analysis Layer (Weeks 1-8)

Phase 1 is read-only. Every scenario this phase pulls data, reasons about it via Claude, and produces structured output - but nothing writes back to ad platforms yet. The goal is a reliable intelligence layer before we touch anything with financial consequences.

Phase 1 exit criteria

By the end of week 8, the system is pulling live data from all three ad platforms, running it through Claude with your exact prompts, producing validated JSON output, creating ClickUp tasks, posting Slack briefings, and enforcing all Phase 1 guardrails - for every client in the KB, on a real schedule.

Week 1 Scenario 1
Environment Setup + Google Ads Ingestion

We start with infrastructure, not code. Google Sheets KB is configured: client config tab, data tabs, schema validated against your design doc. All Make.com connections are established and authenticated. Then we build scenario 1: Google Ads data pull using GAQL queries defined in your spec. Output writes to the KB. Test gate: real data from a single client, output matches expected schema, execution log confirms no rate limit violations.

Week 2 Scenarios 2-3
Meta + LinkedIn Ingestion, Rate Limit Handling

Scenario 2 pulls Meta Ads via Marketing API. Scenario 3 pulls LinkedIn Ads via REST API. Both use the same KB write pattern as scenario 1. Rate limit handling gets built here - not added later. We test the backoff logic by deliberately triggering 429 responses and confirming the retry chain works before either scenario goes to a test gate. Multi-client loop is also tested this week: all KB clients run through both scenarios without one client's failure cascading.

Week 3 Scenario 4
Claude API Integration + JSON Parser

This is the most technically sensitive scenario in Phase 1. We connect the Claude API and implement the JSON parse chain: markdown fence stripping, JSON.parse, schema validation. The prompts come from your design doc verbatim - we don't rewrite them. Error handling covers the two failure modes you care about most: Claude returning free-form text instead of JSON, and Claude returning JSON that doesn't match the expected schema. Both paths route to the dead letter store and trigger a retry with correction prompt. Test gate includes deliberately malformed Claude responses.

Week 4 Scenario 5
First Agent Synthesis Scenario

The first agent scenario reads from the KB (populated by scenarios 1-3), constructs a structured prompt using your client context injection pattern, calls Claude, parses the response, and writes structured output back to the KB. This is the first end-to-end run of the ingestion-to-reasoning chain. We test with a single client first, then run the multi-client loop once the single-client test gate passes.

Week 5 Scenarios 6-7
Additional Agent Scenarios + ClickUp Integration

Scenarios 6 and 7 are additional agent synthesis scenarios covering the other analysis types in your spec. ClickUp integration also goes in this week: the output from agent scenarios maps to ClickUp task creation using the field structure you defined. We confirm task routing, assignee logic, and priority mapping against your design doc before the test gate.

Week 6 Scenario 8
Slack Briefing Scenario + Multi-Client Iteration

Scenario 8 takes agent output and formats it into Slack briefing messages. Message structure follows your spec. We also run the first full multi-client iteration this week: all scenarios 1-8 running in sequence for every client in the KB. The goal is to find any interaction effects between scenarios before adding guardrails - it's easier to debug now than after the conditional logic is in place.

Week 7 Scenario 9
Guardrail Implementation

Scenario 9 implements the Phase 1 guardrails as Make.com conditional modules. Budget ceiling, keyword lock, data threshold, delete lock - all four are structural conditionals in Make.com, not instructions in the Claude prompt. This is deliberate: a guardrail that lives only in the prompt can be reasoned around or ignored when Claude produces unexpected output. A conditional module in Make.com can't be. We test each guardrail by constructing test data that should trigger it and confirming the scenario halts correctly.

Week 8 Scenario 10 + Integration Test
Phase-Level Guardrails + Phase 1 Integration Test

Scenario 10 adds the phase-level guardrails from your spec. Then we run a full Phase 1 integration test: all 10 scenarios, all clients in the KB, on the production schedule. We're looking for timing conflicts, rate limit collisions across scenarios running concurrently, and any KB write conflicts. Blueprint exports for all 10 scenarios are done this week. Week 8 ends with a check-in where we review the full Phase 1 test results together before starting Phase 2.

Phase 2: Controlled Execution (Weeks 9-16)

Phase 2 introduces write operations. The system stops being read-only. Every scenario this phase has an approval gate before anything changes on an ad platform - you confirm before execution runs. We add full autonomy only after the approval-gate versions have passed their test gates.

The approval gate pattern

For every Phase 2 scenario, we build two versions: one that requires approval (routes a proposed action to Slack or ClickUp for your sign-off before executing) and one that runs autonomously once you've confirmed the scenario is stable. You control when each scenario graduates from approval-required to autonomous. We don't flip that switch without your explicit instruction.

Weeks 9-10 Scenarios 11-12
Ad Platform Write Operations - Google Ads + Meta

Scenario 11 writes to Google Ads. Scenario 12 writes to Meta Ads. Both start in approval-gate mode: the scenario generates a proposed change, posts it to Slack with an approve/reject button, and only executes after approval. We test write operations with small budget adjustments on a test campaign before running against live campaigns. The guardrails from Phase 1 are active throughout - a proposed action that violates a guardrail is rejected by the scenario before it even reaches the approval gate.

Weeks 11-12 Scenarios 13-14
Mailchimp Campaign Automation + WordPress Content Updates

Scenario 13 handles Mailchimp: segment selection, campaign creation, and scheduling based on agent output. Scenario 14 handles WordPress content updates. Both use the approval gate pattern. Mailchimp test gate includes confirming that campaign content generated by Claude matches the template structure you've defined and that list segmentation logic is correctly applied. WordPress test gate confirms content updates don't overwrite metadata or custom fields.

Weeks 13-14 Scenario 15
Cross-Agent Coordination + Full Multi-Client Testing

Scenario 15 handles cross-agent coordination: cases where the output of one agent scenario needs to inform the behavior of another in the same run cycle. This is where the system starts to behave more like an integrated intelligence layer than a collection of independent scenarios. We run full multi-client tests across all 15 scenarios this week, specifically looking for timing and state conflicts that only appear at scale. Any issues found here get fixed before week 15.

Weeks 15-16 Scenario 16 + Go-Live
Production Hardening + Documentation Finalization + Go-Live

Scenario 16 is the final orchestration layer - the scenario that coordinates the run order and handles inter-scenario dependencies. Production hardening this week means: schedule conflicts resolved, data store cleanup jobs configured, execution log retention confirmed, and every scenario tested under realistic load. Documentation is finalized: all environment variables, all webhook URLs, all API connections, all blueprint exports. The week 16 check-in is the go-live review. We don't go live until both of us have signed off on the full integration test results.

Weekly Cadence

Here's what a typical build week looks like. The rhythm doesn't change much week to week - predictability is the point.

Monday - Thursday: Build
  • Scenario implementation against spec
  • Error handler construction and testing
  • Multi-client loop testing where relevant
  • Test gate execution on completing scenarios
  • Documentation updated as work proceeds
Friday: Test + Handoff Prep
  • Full test gate run on week's scenarios
  • Execution log review for rate limit timing
  • Blueprint export for completed scenarios
  • Weekly summary drafted for check-in
  • Next week's scope confirmed against timeline
Check-in Meeting
  • Review what shipped and test results
  • Walk through any edge cases found
  • Confirm next week's scope
  • Raise any spec ambiguities before building
  • You can request scope adjustments here
Hours and Pace
  • 15-20 hours per week during active build
  • Heavier weeks: integration tests (wks 8, 14)
  • Lighter weeks: documentation catch-up
  • No billable hours without a completed test gate
  • If a scenario slips, it moves to the next week - timeline doesn't compress
On timeline flexibility

If a scenario takes longer than planned, it shifts the week it completes - it doesn't get shipped without passing its test gate. We'd rather deliver week 8's milestone in week 9 than deliver a scenario that hasn't been properly tested. You'll always know the real status in the weekly check-in, not a polished version of it.
