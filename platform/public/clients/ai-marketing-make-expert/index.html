Multi-client by design

Every scenario reads from a shared Google Sheets knowledge base. Each client is one row in the config tab. The same scenarios run for every client, calibrated by their configuration object. This is not a per-client copy-paste setup.

Technical Challenges We See

This project has three hard problems that separate it from standard Make.com work. All three are solvable, but they need to be handled deliberately.

1
Claude API JSON Parsing
Claude must return valid JSON with a defined schema on every run. Free-form text breaks every downstream module silently. Requires markdown fence stripping and error handling.
2
Structural Guardrails
8 hard-coded guardrails as Make.com conditional modules. Budget ceiling, keyword lock, data threshold, delete lock. In Make.com, not in the prompt, so the AI can't reason around them.
3
Multi-Client Scaling
Scenarios loop through a client list and adapt behavior per config. Rate limiting across multiple ad platform APIs. Error isolation so one client's failure doesn't cascade.
4
Phased Autonomy
Phase 1 is analysis only. Phase 2 introduces controlled execution with go/no-go gates. The autonomy tier matrix (24 action types, 3 phases) must be enforced structurally.

Build Approach

One scenario at a time. Test before connecting to the next. Document everything as we go. This is not negotiable, and it matches how your system design document is structured.

How we work

We follow a spec-driven build methodology: define expected behavior before building, test against the spec (not just "does it run"), and document environment variables, webhook URLs, and blueprint exports at every step. Weekly check-ins with scenario-by-scenario delivery.

  • Your system design doc drives implementation. You wrote the prompts, the schemas, the guardrail specs. We implement them, we don't rewrite them.
  • Each scenario gets a test gate. Before connecting scenario N+1, scenario N must pass its test criteria with real data.
  • Error handlers from day one. Every scenario includes error routing, retry logic for API rate limits, and structured logging.
  • Documentation is a deliverable. Environment variables, webhook URLs, scenario blueprints, and connection inventories are tracked in a shared doc updated weekly.
