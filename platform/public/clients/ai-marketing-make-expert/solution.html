Claude API JSON Parsing

The biggest silent failure mode in any Make.com + Claude integration is malformed JSON. Claude doesn't always return clean JSON - it wraps responses in markdown code fences, adds commentary before the opening brace, or omits fields it thinks aren't relevant. Every downstream module that tries to parse a broken response will fail silently with a null value. By the time you notice something went wrong, the error is two scenarios upstream.

Why this is harder than it looks

Make.com's built-in JSON parser will throw an error on malformed input - that's recoverable. The worse case is when Claude returns structurally valid JSON that's missing required keys. The parser succeeds, downstream modules get null values, and the scenario completes without errors. Nothing in your ClickUp task or Slack briefing is correct. You won't know until a client notices.

The parsing pipeline

We'll build a five-module parsing sequence that sits between the Claude HTTP module and the rest of your scenario logic. It runs on every Claude call, regardless of which agent scenario it's in.

1
Text Template - Prompt Construction

Pulls client config row from Google Sheets (budget limits, active platforms, autonomy tier, branded keywords) and injects into your prompt template. The prompt itself is yours - we're building the injection layer. System message includes the JSON schema with all required fields listed explicitly, plus the instruction: "Respond only with the JSON object. No commentary before or after."

2
HTTP Module - Claude API Call

POST to api.anthropic.com/v1/messages with your model selection, max_tokens, and the assembled messages array. Response stored as raw text in a variable - we don't parse here. We keep the full raw response for the error handler to log if anything goes wrong downstream.

3
Text Parser - Fence Stripping

Regex module strips markdown code fences if present: removes leading ```json or ``` and the trailing ```. Also strips any text that appears before the first { character. Output is a clean string that starts with { and ends with }. This handles Claude's most common deviation from pure JSON output.

4
JSON Parse Module + Router

Make.com's native JSON parse module attempts to parse the cleaned string. The output routes through a filter: if parse succeeded AND all required schema keys exist, continue to scenario logic. If the parse failed or any required key is missing, route to the error path. This is the JSON Validator gate - it checks for key presence explicitly, not just parse success.

!
Error Path - Log and Retry

On parse failure or missing keys: log the raw Claude response to a dedicated "Parse Errors" tab in your Google Sheets knowledge base (timestamp, client, scenario name, raw response, missing keys). Then retry the Claude call once with a stronger instruction appended: "Your previous response was not valid JSON. Respond only with the JSON object matching this exact schema: [schema repeated]." If the retry also fails, the scenario terminates with an error notification to Slack. No silent failures.

5
Downstream Modules

Only scenarios that reach this step have verified, schema-valid JSON. Every field your guardrail modules and action modules reference is guaranteed to exist. This is where the rest of your agent logic begins.

One reusable pattern, used everywhere

We'll build this parsing sequence once as a documented template and apply it to every Claude API call across all 16 scenarios. Scenario 1 gets the full pattern. Scenarios 2-16 copy the template and adapt the schema. If we improve the error handling in Scenario 3, we document the update and apply it backward to Scenarios 1-2.

Structural Guardrail System

You've specified 8 guardrails in your system design document. The implementation detail that determines whether your system is actually safe is where these guardrails live. Here's why that matters, and how we'll build each one.

Prompt instructions aren't guardrails

Telling Claude "don't increase budgets by more than 20%" in a system prompt is a suggestion, not a constraint. Claude can and will reason around prompt instructions when it concludes that a larger change is justified. A structural guardrail is a Make.com filter module that checks the JSON output field against a hard-coded threshold before allowing execution to continue. It can't be reasoned around because it's not in the reasoning layer at all.

Guardrail placement

Every guardrail sits at the same position in the scenario flow: after the JSON Validator gate (so we're reading verified data), and before any write operation (so the write can't proceed if the guardrail trips). Claude makes a recommendation. Make.com checks the recommendation against the guardrail. Only compliant recommendations proceed to execution.

Guardrail What it checks Where it sits On trip
G1 Budget ceiling Proposed budget change ≤ 20% of current Before any ad platform budget write Log + Slack alert, skip write
G2 Branded keyword lock Branded terms not in negative keyword list Before Google Ads keyword updates Strip branded terms, continue with remainder
G3 Minimum data threshold Campaign has minimum impressions/clicks before changes Before any optimization write Pause action, create ClickUp task for manual review
G4 Delete lock Action type is not "delete" - only "archive" or "pause" allowed Before any entity state change Rewrite action to archive, log the override
G5 Phase 1 gate Client autonomy tier permits Phase 1 actions Before all write operations (Phase 1 scope) Block write, generate analysis-only output
G6 Phase 2 gate Client autonomy tier permits Phase 2 actions Before controlled execution writes Route to approval workflow instead
G7 Cross-platform spend Proposed total spend across platforms within client monthly cap Before any budget increase across Google/Meta/LinkedIn Log overage, reduce to remaining budget cap
G8 Content guardrail Ad copy doesn't reference competitor names or prohibited terms Before Mailchimp sends and WordPress updates Flag for human review, hold send
Guardrail state is in Sheets, not in the scenario

Each guardrail threshold (the 20% ceiling, the data minimums, the prohibited terms list) is stored in your Google Sheets knowledge base, not hard-coded in the Make.com filter. This means you can adjust thresholds without editing scenarios. The filter module reads the client's config row and compares against the value in the relevant column. Guardrails stay enforced; thresholds stay configurable.

Multi-Client Architecture

Your system needs to run the same scenarios for multiple clients without any configuration bleeding between them. One client's budget limit can't affect another's analysis. One client's API failure can't cascade into the next client's run. Here's the architecture that makes this work.

Google Sheets as the config layer

The knowledge base has one row per active client. Each row is a complete configuration object for that client's entire system. No client-specific data exists anywhere else in the Make.com scenario logic itself.

Identity columns
Who this client is
  • Client ID (used as a key across all scenarios)
  • Google Ads account ID
  • Meta Ads account ID
  • LinkedIn Ads account ID
  • Active (yes/no for iterator filter)
Guardrail values
Per-client thresholds
  • Monthly budget cap (total)
  • Max single budget change %
  • Data minimum (impressions)
  • Branded keywords list
  • Prohibited content terms
Autonomy config
What the system can do
  • Autonomy tier (1, 2, or 3)
  • Approval email address
  • Slack channel ID
  • ClickUp list ID
  • WordPress site URL

Iterator loop pattern

Each scenario run starts by fetching all rows from the KB where the Active column is "yes". An iterator module loops through those rows, executing the full scenario logic once per client using that client's config object. This is a single scenario handling all clients, not N copies of the scenario running in parallel.

Rate limit handling between clients

Ad platform APIs enforce rate limits per account, but your Make.com scenario is making calls on behalf of multiple accounts in sequence. We'll add sleep modules between iterator iterations - configurable per platform (Google Ads typically needs more breathing room than Meta). The sleep duration is stored in a scenario-level variable so we can tune it without touching the iterator logic.

Error isolation

This is where most multi-client Make.com setups fail. If client 3's Google Ads account has an authentication error and the scenario throws an exception, the default behavior stops the entire iterator - clients 4, 5, and 6 never get processed.

We'll wrap the per-client logic in an error handler module. If any module within the client block fails, the error handler catches it, logs the client ID and error to a "Failed Runs" tab in Sheets, posts a Slack alert, and marks that iteration as failed. The iterator then continues to the next client. At the end of the run, a separate error recovery scenario checks the Failed Runs tab and retries any clients that failed in the previous run.

A
Per-client error handler
Wraps all client-specific API calls. Catches auth errors, timeout errors, and rate limit responses. Logs structured error records to Sheets with client ID, timestamp, module name, and error code.
B
Error recovery scenario
Runs on a delayed schedule (2 hours after the main run). Reads the Failed Runs tab, filters for unresolved errors, and retries those specific clients only. Marks retried entries as resolved or escalates to Slack if the retry also fails.
C
Client health dashboard tab
A Sheets tab that shows the last successful run timestamp per client. Any client with a gap larger than 2x the expected run interval gets flagged automatically by a formula. No manual checking required.
D
Onboarding pattern
Adding a new client means adding a row to the KB and filling in the config columns. No scenario edits needed. The iterator picks up new active rows on the next scheduled run automatically.

Phased Autonomy Model

Your system design specifies three phases of autonomy. The implementation question is how to enforce these boundaries so that a Phase 1 client can't accidentally get Phase 2 behavior if something changes, and a Phase 2 client's approval workflow can't be bypassed.

What each phase means in Make.com terms

Phase 1 - Read only
Analysis and reporting
  • All ad platform calls are GET requests only
  • Claude analyzes data, creates tasks, posts Slack briefings
  • No write operations to any ad platform
  • ClickUp tasks generated for human execution
  • Full data pipeline active - no execution
Phase 2 - Gated execution
Approved writes only
  • Claude recommends a change with JSON payload
  • Guardrail check runs before approval request
  • Approval sent via Slack or email with approve/reject link
  • Webhook waits for approval response (24hr timeout)
  • Write executes only after approval confirmed
Phase 3 - Autonomous
Within guardrail boundaries
  • Guardrail check runs before every write
  • Compliant changes execute immediately
  • Non-compliant changes route to approval workflow
  • All writes logged to audit trail in Sheets
  • Weekly summary sent regardless of action volume

Autonomy tier matrix

The 24 action types across your system each have a maximum autonomy level. The Make.com filter that enforces this reads the client's tier from the KB and compares it against the action's maximum allowed tier. If the client's tier is lower than the action requires, it routes to the appropriate fallback.

Phase upgrades don't require scenario changes

When you're ready to move a client from Phase 1 to Phase 2, you update their autonomy tier in the Google Sheets KB from "1" to "2". The filter modules in every scenario read that value on each run. No scenario editing, no blueprint changes, no redeployment. The client's next scheduled run picks up the new tier automatically.

The approval workflow (Phase 2)

When a Phase 2 client's scenario reaches a guardrail-compliant write action, it doesn't execute. Instead it sends an approval request and waits.

  • Approval request format: Slack message with a summary of the proposed change, the Claude reasoning behind it, the guardrail check result (passed), and two buttons - Approve and Reject. Alternatively, email with the same content and approve/reject links that trigger a webhook.
  • Webhook listener: Make.com scenario watching for the approval response. On approval, it executes the write with the exact payload from the original recommendation. On rejection, it logs the rejection and creates a ClickUp task with the rejected recommendation for manual review.
  • Timeout handling: If no response arrives within 24 hours, the scenario logs the pending approval as expired and moves on. A daily digest lists all expired approvals so nothing gets lost in the queue.
