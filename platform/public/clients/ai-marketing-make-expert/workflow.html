Our Build Methodology

Your 1,300+ paragraph system design document is the specification. We don't reinterpret it or improvise around it - we implement against it. The prompts you wrote, the JSON schemas you defined, the guardrail specs you laid out: those are the source of truth. Our job is to translate them into working Make.com scenarios.

Why this matters for your project

Most freelancers who build Make.com automations treat the client's description as a rough brief and fill in the gaps themselves. Your system doesn't have gaps to fill - it has a design document. We treat that as a spec, not a starting point for creative interpretation.

The build follows three principles:

  • Scenario-by-scenario delivery. We complete and test each scenario before starting the next. You can see working output at every stage, not just at the end.
  • Weekly check-in cadence. Every week: what shipped, what's being tested, what's next. You're never in the dark about where we are in the sequence.
  • No deferred error handling. Error routers, retry logic, and dead letter logging get built into every scenario from the start - not bolted on at the end when something breaks in production.

This isn't a methodology we invented for this proposal. It's how we build every multi-scenario system. The alternative - building all 16 scenarios in a batch and testing at the end - produces a debugging nightmare that nobody wants at week 15.

Test Gates

Before we connect scenario N+1, scenario N has to pass five criteria. All five. Not four out of five.

  • 1
    Runs successfully with test data from the KB. We use real records from your Google Sheets knowledge base as test inputs - not synthetic data we made up. If the scenario can't handle your actual data format, we catch it here.
  • 2
    JSON output matches the expected schema. For any scenario that produces Claude API output, we validate the parsed JSON against the schema defined in your design doc. Field names, types, required fields - all checked. A Claude response that compiles but drifts from the schema fails this gate.
  • 3
    Error handler catches all known failure modes. We deliberately trigger the error paths: bad API key, rate limit response, malformed JSON from Claude, empty data set, missing KB row. Each one has to route to the error handler correctly before we move on.
  • 4
    Rate limits respected, verified via execution log timing. For data ingestion scenarios hitting Google Ads, Meta, and LinkedIn, we check the execution log to confirm request spacing matches the platform's documented limits. This is especially important for multi-client loops where one slow client can push all subsequent requests into a rate limit window.
  • 5
    Documentation updated before moving on. Environment variables added this session, webhook URLs generated, API connection names, blueprint JSON exported - all logged before scenario N+1 starts. Documentation written after the fact is always incomplete.
On the "runs successfully" criterion

A scenario that runs without throwing an error is not the same as a scenario that produces correct output. We check both. An incorrectly parsed Claude response that still passes through the Make.com flow is a silent failure - the worst kind for a system that's supposed to make autonomous decisions.

Error Handling Patterns

Every scenario has an error router on every module that touches an external API. Not just on the final output module - on every step that can fail. Here's what that looks like in practice for your system.

API Rate Limit Detection and Retry

Google Ads, Meta, and LinkedIn all return 429 errors when rate limited. We handle these with exponential backoff in Make.com: catch the 429 in the error router, wait (starting at 5 seconds, doubling on each retry), retry up to three times, then route to the dead letter store if all three fail. This runs inside the scenario itself - you don't need a separate retry scenario.

Claude Response Validation

Claude's API responses aren't always clean JSON. Sometimes the model wraps output in markdown fences even when instructed not to. Sometimes it adds commentary before the JSON object. We handle this with a three-step parse chain in Make.com: strip markdown fences, attempt JSON parse, validate against the schema. If the parse fails, we retry the Claude API call once with an error correction prompt. If the second attempt also fails, we route to the dead letter store and send a Slack alert. We never pass a failed parse downstream - that's how silent errors enter the system.

Dead Letter Logging

Failed runs don't just disappear. Every error gets written to a dedicated data store with: scenario name, client ID, timestamp, error type, the input payload that caused the failure, and the full error message. This gives us a complete debugging record without having to reconstruct what happened from Make.com's execution history (which has retention limits and isn't always readable under pressure).

Slack Notification on Critical Failures

Critical failures - anything that affects a client's ad spend, campaign status, or scheduled deliverable - trigger a Slack alert. Non-critical failures (a single analytics pull that failed and will retry at the next scheduled run) log to the dead letter store but don't page. We'll agree on the threshold for "critical" during setup so you're not getting noise alerts for transient API timeouts.

Transient Failures
Auto-retry
  • 429 rate limit responses
  • Timeout errors
  • Temporary API outages
  • Claude JSON parse failure (1 retry)

Documentation as a Deliverable

Documentation isn't something we do at the end. It's updated every week as part of the delivery. By the time we reach week 16, you have a complete operational record of every scenario - not a rushed summary written during handoff.

What gets documented per scenario

Configuration
  • All environment variables added
  • API connection names in Make.com
  • Webhook URLs generated
  • Data store names and structure
  • Google Sheets tab and column references
Test Results
  • Test data used (KB row IDs)
  • Output samples from passing runs
  • Error paths verified
  • Rate limit timing from execution log
  • Schema validation pass/fail record
Operational Notes
  • Known limitations or edge cases
  • Retry limits and backoff settings
  • Dead letter store location
  • Slack alert configuration
  • Schedule and trigger configuration
Blueprint Export
  • JSON blueprint exported at completion
  • Stored in shared tracking doc
  • Re-exported at every major milestone
  • Versioned so rollback is possible
  • Importable to a fresh Make.com org
Why blueprint exports matter

Make.com doesn't have native version control. If a scenario gets edited incorrectly - or if you ever need to move to a different Make.com organization - blueprint exports are your backup. We export after every scenario is completed and after every integration test. You'll always have a known-good restore point.

Documentation is maintained in a shared tracking doc that both of us can see. It's not something we send you at the end of the project. It's live throughout the build. That means you can review what was deployed at any time, not just during our weekly check-in.
