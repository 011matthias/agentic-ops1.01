What You're Building

A fully autonomous marketing agency system where AI agents handle the full cycle - pulling performance data, reasoning about what to do, creating tasks, sending briefings, and eventually executing changes directly. Autonomy Phases

The three-phase autonomy model is the core design constraint: Phase 1 observes and reports, Phase 2 acts with approval gates, Phase 3 acts autonomously within guardrails. Each phase expands what the system is allowed to do. The guardrails define the ceiling, not the floor.

Phase 1
Analysis only
Data in, insights out. No writes to any platform. Scenarios 1-10.
Phase 2
Controlled execution
Writes allowed with go/no-go gates. Human approval in the loop for higher-risk actions. Scenarios 11-16.
Phase 3
Autonomous
Full execution within the hard guardrail boundaries. No approval gates for pre-cleared action types.

Guardrail Specification

You mentioned 8 guardrails. Based on the platforms and autonomy model described, here's what we expect them to cover. These are implemented as Make.com conditional modules, not prompt instructions. The AI can't reason around them because they're not part of the prompt - they're structural gates in the scenario flow.

  • 1
    Budget ceiling Blocks any spend increase beyond a configurable percentage of the client's current budget. Per-client threshold stored in KB config tab.
  • 2
    Keyword lock Prevents modification or deletion of keywords flagged as protected in the KB. No AI reasoning overrides this.
  • 3
    Data freshness threshold Blocks analysis execution if the input data is older than a configurable window. Prevents decisions based on stale performance data.
  • 4
    Delete lock Hard block on any delete operation across all platforms at all autonomy phases. Deletion always requires manual action.
  • 5
    Phase gate Execution scenarios check the client's current autonomy tier before running write operations. A Phase 1 client can't receive Phase 2 actions regardless of what Claude recommends.
  • 6
    Single-run limit Caps the number of changes the system can make in a single execution cycle per client. Prevents runaway batch operations.
  • 7
    Platform activation check Scenarios only execute against platforms listed as active for that client in the KB. Inactive platform columns are skipped entirely.
  • 8
    Client active flag A single on/off switch per client row in the KB. When off, all scenarios skip that client entirely, regardless of other config values.
Guardrails 5-8 are inferred

Guardrails 1-4 you described directly. Guardrails 5-8 are what we'd build into a system like this based on the architecture. If your spec defines different guardrails for slots 5-8, those override our assumptions completely.
