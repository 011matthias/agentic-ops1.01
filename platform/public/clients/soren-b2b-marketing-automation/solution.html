Architecture Decisions

What gets built, which platform handles what, and why. This page covers the structural choices. The Workflow page shows how data actually moves through the system with concrete examples.

Platform Split

Two platforms, each doing what it does best. Not because complexity is the goal, but because no single platform handles both API integrations and custom logic well enough.

Make.com Integration Layer

  • Webhook endpoints for each lead source
  • Apollo API calls for enrichment
  • CRM reads and writes (HubSpot, Pipedrive, or your choice)
  • HeyReach API triggers for LinkedIn outreach
  • Google Sheets logging and config reads
  • Scheduled data pulls (Apollo lists, ad platform exports)
  • Email sending via SMTP module

n8n Logic Layer

  • Lead scoring calculations (code node)
  • Conditional routing based on score bands
  • Sequence management (day offsets, channel order)
  • Reply detection via IMAP polling
  • Retry logic for flaky third-party APIs
  • Deduplication checks against CRM
  • Custom data transformations

How they talk to each other: Make.com captures and normalizes incoming leads, then fires a webhook to n8n with the normalized record. n8n scores it, decides the routing, and fires a webhook back to Make.com to update the CRM and trigger the right outbound sequence. Two handoffs, both via webhook, both logged.

50+ Make.com scenarios in production

This isn't a hypothetical architecture. I've built and maintained 50+ Make.com scenarios across client projects, including multi-scenario pipelines that process real leads daily. The patterns here come directly from what's working.

Comet Browser: three integration paths

Comet Browser doesn't have a documented public API, which means the integration path depends on how your team uses it. Three options, depending on what we find during onboarding:

Path 1: If Comet Browser supports webhook callbacks (event fires when a prospect engages), we wire those directly into Make.com as another lead source. Same pattern as HeyReach.

Path 2: If it has CSV or data export, we schedule automated imports via Make.com. Run hourly or daily, pull new records, normalize, and feed into the pipeline.

Path 3: If it's browser-only with no data export, we can use Playwright to automate data extraction. That's a Phase 3 conversation after we understand your specific Comet workflow. The onboarding form asks about this specifically.

Data Architecture

Every lead source produces different data. LinkedIn gives you a name and company. Apollo gives you a full firmographic profile. A web form gives you whatever the prospect typed. Before any scoring or routing happens, everything gets normalized into one schema.

Target lead schema

This is the canonical record format that all sources normalize to. After normalization, every lead looks the same regardless of where it came from.

{
  "email": "jane.chen@acme.io",
  "first_name": "Jane",
  "last_name": "Chen",
  "company": "Acme Corp",
  "title": "VP Marketing",
  "company_size": "200-500",
  "industry": "SaaS",
  "seniority": "VP",
  "source_channel": "linkedin_heyreach",
  "capture_ts": "2026-04-01T10:23:00Z",
  "enrichment_status": "complete",
  "lead_score": null
}

Source-to-schema mapping

Each source has different field names. Here's how they map:

Schema Field LinkedIn (HeyReach) Apollo Web Form
email prospect.email person.email form.email
first_name prospect.firstName person.first_name Split from form.name
company prospect.companyName person.organization.name form.company
title prospect.title person.title form.role (if provided)
company_size Needs enrichment person.organization.estimated_num_employees Needs enrichment
industry Needs enrichment person.organization.industry form.industry (if provided)
source_channel Set to "linkedin_heyreach" Set to "apollo_import" Set to "web_form"

Fields marked "Needs enrichment" get filled by the Apollo API call. If Apollo can't find the person, those fields stay empty and the lead gets flagged as enrichment_status: "partial" for manual review.

Where data lives

  • CRM is the system of record for leads, pipeline stages, and contact history
  • Google Sheets holds configuration (scoring weights, sequence cadence, routing rules) and activity logs
  • Make.com data stores handle deduplication lookups and temporary queue state
  • n8n doesn't persist data between runs. It reads from CRM, processes, and writes back
You own all the data

Nothing lives in a proprietary system you can't access. CRM data is yours. Google Sheets are in your Drive. Make.com and n8n configurations export as JSON. If you ever want to move off this stack, everything comes with you.

Blueprint Deep-Dive

The downloadable blueprint is a Make.com scenario you can import into any account. It covers the core capture-and-enrich flow. Here's what each module does and what you'd need to configure.

Module 1 Custom Webhook

Listens for incoming HTTP POST requests. Expected fields: email (required), name, company, source.

To configure: After importing, Make.com generates a unique webhook URL. Point your form handler, HeyReach webhook settings, or any other lead source at this URL.

Module 2 Router

Splits the flow into branches. Currently one branch (the enrichment path). In the production version, you'd add branches for: already-enriched leads (skip Apollo), leads with missing email (route to review), and error handling.

Module 3 HTTP: Apollo Enrichment

Sends the lead's email to Apollo's /v1/people/match endpoint. Returns the full person object: company name, title, seniority, company size, industry, and technology stack.

To configure: Replace {{parameters.apolloApiKey}} with your Apollo API key. If Apollo can't find the person, it returns a 404. The production version adds an error handler for this.

Module 4 JSON Parser

Parses Apollo's response body into individual fields that downstream modules can reference. No configuration needed.

Module 5 HTTP: CRM Push

Creates a new contact in HubSpot (or your CRM) with the enriched data. Maps email, name, company, title, lead source, and initial score (set to 0 before n8n scoring runs).

To configure: Replace {{parameters.hubspotToken}} with your CRM access token. If you use Pipedrive or another CRM, the endpoint URL and field names change, but the pattern is the same.

What's intentionally missing from this blueprint

This is a starter, not the production scenario. The production version adds: error handling branches for API failures, deduplication checks before CRM write, rate limit management for Apollo, Google Sheets logging, and the webhook to n8n for scoring. Those get built during Phase 1 of the engagement, configured to your specific tools and thresholds.

Why This Stack

The obvious question: why two platforms? Why not Zapier? Why not build everything custom?

Why not Zapier alone

Zapier caps operations at plan-level limits that get expensive fast with a multi-source lead pipeline. More importantly, Zapier doesn't support custom code nodes. When you need to calculate a lead score using weighted firmographic and engagement signals, you need a code node. Zapier would force you to use an external function service, adding a third system to maintain.

Why not all Make.com

Make.com is excellent at connecting APIs. It's not great at running custom logic. Lead scoring that weighs 10+ signals across two categories, with thresholds that change as you learn what converts, needs a code node with real JavaScript. Make.com's "Set Variable" and "Switch" modules can technically do it, but the resulting scenario is fragile, hard to debug, and painful to modify when scoring rules change.

Why not all n8n

n8n can do API integrations, but its native module library is smaller than Make.com's. Apollo, HeyReach, and most CRMs have native Make.com modules with built-in auth management and error handling. Building those integrations from scratch in n8n using HTTP nodes works but takes more setup time and requires manual credential management.

Why not custom code

You could build this as a Node.js or Python application. The problem: you'd need someone to maintain it. When Apollo changes their API, someone has to update the integration code. When you want to add a new lead source, someone has to write the handler. With Make.com and n8n, those changes are visual edits, not code deployments. Your team can see what's happening without reading source code.

The right amount of infrastructure

Two platforms is the minimum for this pipeline. Make.com handles what it's best at (API connections), n8n handles what it's best at (logic), and you can see everything that's happening in both dashboards without SSH-ing into a server.
