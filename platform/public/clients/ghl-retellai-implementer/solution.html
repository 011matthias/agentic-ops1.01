The Data Flow

Each voice call your agency delivers follows the same path: a GoHighLevel pipeline event triggers an n8n workflow, which calls Retell AI, which calls back with results, which n8n routes into GHL updates and follow-up actions. Here's each step with enough detail to evaluate whether I understand your architecture.

1
GHL Pipeline Event

A contact hits a pipeline stage in GoHighLevel. GHL fires an outbound webhook to an n8n webhook URL with the contact payload: name, phone, email, custom field values, and the pipeline stage that triggered it. The webhook URL is configured per pipeline stage in GHL's automation settings, which means each client sub-account needs its own URL pointed at the correct n8n instance.

2
n8n Receives and Routes

The n8n Webhook node catches the incoming payload. A validation step checks that required fields are present (phone number, pipeline stage, contact ID). Then a Switch or IF node routes by stage name: some stages trigger a Retell voice call, others trigger an SMS-only sequence, and some skip automation entirely. GHL has a native n8n node, so contact lookups and updates use structured fields rather than raw HTTP requests.

3
Retell API Call

n8n calls Retell's create-call endpoint via HTTP Request node with the contact's phone number and a set of dynamic variables: client name, services they've expressed interest in, available appointment slots, and any client-specific context. These variables are injected into Retell's general_prompt field, which means the voice agent's script adapts per call without needing a separate agent per scenario.

4
Voice Agent Executes

The Retell AI agent runs the call using a configured ElevenLabs voice. The system prompt has the injected variables baked in, so the agent speaks with context about the specific lead. The agent navigates objections, qualifies the lead against criteria defined in the prompt, and attempts to book or hand off. Voice selection and conversation style are configured per client in the Retell dashboard.

5
Webhook Callback

Retell sends three separate webhook events back to n8n for every call: call_started (call initiated), call_ended (call finished, includes duration), and call_analyzed (transcript, outcome classification, structured data from the conversation). All three arrive at the same n8n webhook endpoint. Retell enforces a 10-second timeout on webhook delivery and retries up to 3 times on failure, so the n8n endpoint needs to respond quickly.

6
Filter and Update

An IF node filters for call_analyzed events only, ignoring the other two. From the analyzed payload, n8n extracts the full transcript, the outcome classification (booked, not interested, voicemail, callback requested), and any structured data the agent captured during the conversation. The GHL native node then updates the contact record: call outcome in a custom field, transcript in notes, and pipeline stage moved to reflect the result.

7
Follow-up Actions

Based on the call outcome, n8n branches into follow-up paths. A booked appointment triggers a Twilio confirmation SMS with the appointment details. A callback request updates the Supabase state record and schedules a re-trigger. Every call, regardless of outcome, syncs a row to the Airtable reporting table with timestamp, duration, outcome, and client ID. Each branch is configurable per client without touching the core workflow logic.

Why n8n is the right backbone here

n8n gives you execution-level visibility into every step. When a call doesn't fire or a contact doesn't update, the execution log shows exactly which node failed and what data it received. That's the difference between "something broke" and "the GHL webhook sent an empty phone field on contact #4521 at 2:14pm." I can diagnose issues from the log without asking you to reproduce anything.

Webhook Architecture

There are five webhooks in the system. Understanding where each one lives and what constraints it operates under is what makes debugging fast and setup reliable.

Webhook Source Destination Payload Constraint
Pipeline stage trigger GoHighLevel n8n Webhook node Contact data + pipeline stage + custom fields URL is per sub-account. Does not carry over from snapshot clone.
call_started Retell AI n8n Webhook node Call ID, agent ID, phone number 10s timeout, 3 retries. Filtered out by IF node.
call_ended Retell AI n8n Webhook node Call ID, duration, end reason 10s timeout, 3 retries. Filtered out by IF node.
call_analyzed Retell AI n8n Webhook node Transcript, outcome classification, structured data 10s timeout, 3 retries. This is the event n8n acts on.
Error notification n8n error trigger Slack or email Workflow name, error message, failed node, execution ID Fires on any workflow execution failure. Separate workflow.
The 10-second constraint

Retell's webhooks time out after 10 seconds and retry up to 3 times. That means the n8n workflow receiving callbacks needs to respond with a 200 status immediately and process the payload asynchronously if any downstream step (GHL update, Airtable sync) might be slow. In practice, n8n handles this naturally because each node executes sequentially after the webhook responds. But if you add a slow external call before the response, you'll see duplicate events from retries. I'll set this up correctly from the start.

Client Onboarding Flow

Each new client starts from a master GoHighLevel snapshot. The clone itself takes minutes. What takes 3-4 hours is everything that doesn't carry over.

What carries over vs. what doesn't

Component Carries over Notes
Pipelines and stages Yes Full pipeline structure transfers intact.
Sequences and timing Yes Email/SMS sequences transfer with timing rules.
Custom fields Yes Field definitions transfer. Values don't (expected).
Funnel structure Yes Page layout and forms transfer.
Webhook URLs No Every webhook URL must be reconfigured to point at the new n8n workflow instance.
Integration credentials No OAuth connections, API keys, and third-party auth need re-setup under the new sub-account.
Custom field mappings Partial If the client's data structure differs from the master, field mappings in n8n need updating.
1
Clone Master GHL Snapshot

The master snapshot is cloned into a new sub-account. Pipelines, sequences, custom fields, and funnel structure all transfer over. This step takes a few minutes and is handled in the GHL admin panel.

2
Post-Snapshot Reconfiguration

This is where the 3-4 hours go. Each webhook URL needs to be reconfigured to point at a new n8n endpoint. Integration credentials (OAuth for GHL API, Retell API key, Twilio SID) need to be set up under the new sub-account. If the client has non-standard custom fields, the n8n field mappings need adjusting. Each item is individually verified after configuration.

3
Configure Retell Agent

A new Retell AI agent is set up for the client: system prompt tailored to their industry and services, ElevenLabs voice selected, dynamic variable mappings defined (which GHL fields feed into the call context), and the callback webhook URL pointed at the correct n8n instance.

4
Create n8n Workflow Instances

n8n workflows are cloned from a template and configured for the new client: unique webhook paths (so callbacks route correctly), fresh credential bindings for GHL and Retell, Airtable base ID pointed at the client's reporting table, and Supabase table references updated. Each workflow gets a client-prefixed name for easy identification.

5
End-to-End Test

A test lead is created in GHL and moved through the trigger pipeline stage. The webhook fires, the Retell call executes (to a test number), and n8n processes the callback. The GHL contact record is checked for the correct custom field update, the Airtable reporting row is verified, and the Twilio SMS is confirmed delivered. Pass, or document exactly which step failed and why.

Reducing setup time over time

The 3-4 hour reconfiguration is the current baseline. As I work through multiple setups, I'll build n8n workflow templates with parameterized credential bindings and webhook paths. The goal is to reduce the manual reconfiguration to a checklist of values to fill in rather than a sequence of steps to remember. I'll flag these template improvements as I find them.

Ongoing Maintenance

Your posting mentions 2-3 change requests per client per week. Here's what that volume actually looks like broken down by category, with the typical turnaround for each.

Prompt refinements

The most common request. A call recording surfaces an edge case: the agent mishandled a specific objection, used the wrong framing for a particular industry, or failed to capture a piece of information. The fix cycle is short: listen to the call or read the transcript, identify the gap in the system prompt, update the prompt text, trigger a test call to verify the new behavior, and confirm. Most prompt refinements take 30-60 minutes including the test call.

Workflow updates

New business logic that changes how n8n processes calls. Adding a new trigger condition (a pipeline stage that didn't previously trigger a call), capturing an additional data field from GHL and writing it to Airtable, modifying routing rules when a client changes their pipeline structure, or adding a new SMS branch via Twilio for a specific call outcome. These involve editing the n8n workflow, testing with a sample payload, and verifying the downstream data lands correctly.

GHL pipeline and sequence adjustments

Clients refine their sales process, which means GHL changes. A pipeline stage gets renamed (which breaks the n8n Switch node if it matches on stage name), a sequence timing changes, or a new custom field needs to be added and pulled into the Retell dynamic variables. These require coordinated changes across GHL and n8n to keep them in sync.

Debugging

Failed webhooks, expired GoHighLevel OAuth sessions, Retell API timeouts, or a Twilio delivery failure. Debugging follows the data path: check the GHL event log for the outbound webhook, check the n8n execution log for the receiving workflow, check the Retell API response for the call attempt, and check the callback event for the result. Each system has its own log, and the contact ID ties them together. Most issues are identifiable within 15-20 minutes of the report.

What a typical week looks like

Monday: prompt refinement for an appointment setter that didn't handle a scheduling conflict. Wednesday: add a new custom field from GHL to the Airtable sync for a client who started tracking lead source. Thursday: debug an expired OAuth token on a client sub-account that stopped webhook delivery. Friday: update a Switch node after a client renamed their "Qualified" pipeline stage to "Ready to Call." Each of these is handled async with a written update on what changed and why.
