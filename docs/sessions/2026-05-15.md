## Self-anneal: reasoning review (Layer 2) on the verification-theater event

**Trace:** I assumed `vercel --prod --force` resulted in a stable production deployment because the command output said "Aliased: https://unpauseai.com" and one WebFetch returned 200. I never re-verified after Vercel's git-integration could have finished a concurrent rebuild.

**Audit the verification method:** A single 200 at one moment is state-checking, not behaviour-checking over a window. The behaviour I needed to verify was "production alias remains pointed at the deployment containing the new file." That's a different question.

**Attribution direction:** When the URL went 404, my initial diagnosis leaned toward "CDN edge cache holding stale 404" before considering "Vercel may have replaced my deployment with a newer one." That's an external-system suspicion before questioning my own recent action (and Vercel's concurrent autonomous action). The agent's own deploy plus Vercel's autonomous rebuild were the two most likely causes; I anchored on the third (CDN cache) first.

**Compiles vs works:** I treated "deploy command succeeded" + "one WebFetch returned 200" as "URL works in production." The deploy itself worked (technically successful). The post-deploy state was unstable due to a separate process running concurrently.

**Transferable principle:** **State at one moment is not equivalent to state over a window when multiple processes can modify the same resource.** When verifying a deploy on a platform where concurrent autonomous rebuilds can fire (Vercel git integration, GitHub Actions, etc.), the verification has to include "no other actor will replace this state in the next few minutes"; typically by polling the deployment-list and confirming no newer deployment supersedes the one you intended.
